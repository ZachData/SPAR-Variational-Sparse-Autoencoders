## 0. The seed-collision landmine reappears in the ANALYSIS step

**Status: found before it did damage. `run_overnight.sh` analysis block needs the fix below.**

`run_arm.py` defeats the known landmine by giving each run its own `save_dir`. The
analysis step undoes it. `online_histogram_analyzer.py` writes to
`<output-dir>/<model_name>/`, where `model_name` is the checkpoint directory's name
(`get_model_name()`, line 261) — and since `get_experiment_name()` omits the seed,
**every seed of an arm has the same `model_name`**:

    experiments/baseline/seed1/TopK_KL_gelu1l_d2048_k256_auxk0.03125_pen0.0_lr0.0008/
    experiments/baseline/seed2/TopK_KL_gelu1l_d2048_k256_auxk0.03125_pen0.0_lr0.0008/
    ...                        ^ identical for all six seeds

With the default `--output-dir ./comprehensive_histogram_analysis`, all six seeds
write the same `comprehensive_summary_<model_name>.json`, each overwriting the
last. The result is **one summary per arm instead of six** — the exact failure the
landmine warns about, at the one step where the per-seed `save_dir` does not
protect you. It would not have errored; it would have quietly produced a seeded
design with n=1 per arm, and the permutation tests would have had nothing to
permute.

Two further defects in the same block, both of which would have failed all 30 calls:

* **Wrong `--model-path`.** The sweep passes the checkpoint's parent, but
  `load_dictionary()` needs the directory holding `ae.pt` and `config.json`
  directly — `trainer_0/`. The analyzer even anticipates a `trainer_0` argument.
* **`import dictionary_learning` failed.** Running
  `python analysis_scripts/online_histogram_analyzer.py` from the repo root puts
  `analysis_scripts/` on `sys.path`, not the repo root, so the invocation
  documented in RUNBOOK.md and CLAUDE.md raised `ModuleNotFoundError`. Fixed by
  adding the same `sys.path` bootstrap `run_arm.py` uses. `seaborn` was also
  missing and is now installed.

The corrected invocation, one output directory per seed:

```bash
python analysis_scripts/online_histogram_analyzer.py \
  --model-path experiments/<arm>/seed<N>/<ckpt>/trainer_0 \
  --output-dir experiments/<arm>/seed<N> \
  --n-samples 1000000 --no-individual
```

`--n-samples 1000000` must be identical for every checkpoint: `features_used` is
sample-size dependent and comparability across arms depends on it.

## 1. `min_p_floor` / `min_attainable_p` have one-sided and two-sided swapped

**Status: unfixed. Affects planning tables, not results.**

`permutation.min_p_floor` and `evalues.min_attainable_p` both compute the smallest
attainable p-value as `1/N` for two-sided and `1/(N//2)` for one-sided, where
`N = C(n_a+n_b, n_a)`. Exact enumeration attains the opposite: **1/N one-sided**
(only the observed assignment beats itself) and **2/N two-sided** (an assignment
and its complement always tie on `|stat|`, so the count is never less than 2).

Measured, 3 seeds per group, `N = 20`:

| alternative | p attained by `seed_permutation_test` | p_floor reported |
|---|---|---|
| `greater` | 0.0500 (= 1/N) | 0.1000 |
| `two-sided` | 0.1000 (= 2/N) | 0.0500 |

So a one-sided seed test can and does **return a p-value below its own reported
floor** — the invariant a floor exists to express.

**What is and is not affected.** The decision rule uses the real `p_value`, which
comes from honest enumeration and is valid, so no e-value, no `SequentialFalsifier`
verdict, and none of the sweep's results are wrong because of this. What is wrong
is every number derived from the floor: the PROJECT.md table ("distinct splits /
min attainable p / e-value"), the RUNBOOK power table, and `seeds_required()`.
They are **2x pessimistic** for the one-sided tests the design actually uses.

**The headline planning conclusion survives.** Corrected, 5 seeds/group attains
p = 1/252 → e = 7.94 at κ=0.5, still short of the threshold of 10; 6 seeds attains
p = 1/924 → e = 15.2. So "5 seeds cannot validate on a single test, 6 can" holds
either way. The intermediate numbers quoted in the tables do not.

**Left unfixed deliberately.** The correction changes the pre-registered power
accounting, and α and κ are pre-registered. Fixing it is a decision for the author,
not something to change mid-sweep. Pinned by
`test_p_value_never_falls_below_its_own_reported_floor`, an `xfail(strict=True)` in
`falsification/tests/test_permutation.py` that will fail loudly once fixed, so the
marker cannot outlive the bug.

## 3. All loss terms were discarded whenever wandb was off

**Status: fixed in `dictionary_learning/training.py`.**

`log_stats()` computed the full loss dict (`l2_loss`, `auxk_loss`,
`activation_cost`, `loss`, `effective_l0`, `dead_features`) and forwarded it
**only to the wandb queue**. With `use_wandb=False` — which is exactly what
`run_arm.py` sets for unattended runs — `log_queues` is empty and every term was
dropped. The only output was `Step N: L0 = ..., frac_variance_explained = ...`.

Consequence: the canary check specified for E1 ("confirm `activation_cost` appears
in the logged losses and is non-zero") was **unsatisfiable as written**, and a
10-hour unattended sweep would have recorded no loss history at all.

The `verbose` branch now prints every term. Confirmed in a real run:

```
Step 0:    ... activation_cost=0.9219, loss=2.2500
Step 6000: ... activation_cost=0.0537, loss=0.1406
```

**The penalty itself was always correctly wired** — this was purely an
observability defect. Verified directly against the trainer: at
`activation_penalty=1.0`, `activation_cost = 511.05` and
`l2_loss + auxk_alpha*auxk_loss + activation_cost` reproduces the logged total to
4 decimals; at `0.0` it is exactly `0.0`. **E1 is sound.**

## 6. E2 result: it is mu that collapses, not sigma — and the arm is confounded by beta

**All 6 seeds, measured at step 9000. Not yet the pre-registered analysis; these are
the training diagnostics the logging fix made visible.**

| seed | `mean_var` | `mean_mu_magnitude` | `kl_mu_term` | `kl_var_term` | FVE | `frac_recovered` |
|---|---|---|---|---|---|---|
| 1 | 0.5469 | 0.0004 | 0.0000 | 214 | 0.0001 | -0.741 |
| 2 | 0.5352 | 0.0007 | 0.0000 | 241 | 0.0001 | -0.738 |
| 3 | 0.5547 | 0.0012 | 0.0000 | 220 | 0.0001 | -0.719 |
| 4 | 0.5469 | 0.0012 | 0.0000 | 238 | 0.0001 | -0.746 |
| 5 | 0.5391 | 0.0008 | 0.0000 | 227 | 0.0001 | -0.743 |
| 6 | 0.5547 | 0.0018 | 0.0000 | 225 | 0.0001 | -0.730 |

Near-zero across-seed variance. Three things follow.

**PROJECT.md's stated diagnostic does not fire, and its converse does.** E2 was
framed as: "if the learned sigma collapses toward 0, the degeneracy is the
*optimum* rather than an implementation accident." Sigma does **not** collapse —
it sits at variance ~0.54 against a prior variance of 1. What collapses is **mu**,
to ~1e-3, driving `kl_mu_term` to exactly 0. The entire KL is the variance term.
This is textbook posterior collapse: the encoder stops encoding and matches the
prior. So the stronger result PROJECT.md hoped for is not available, and the
question "is the degeneracy the optimum?" is not answered by this arm.

**The model is destroyed, not merely degraded.** FVE = 0.0001 and
`frac_recovered` ~ -0.74: substituting the vSAE's reconstruction is *worse than
ablating the activation to zero*. A model in this state has no feature structure to
compare against anything.

**The arm is confounded by beta, and the confound is structural.**
`kl_coeff = 1.0` is not the same intervention at `var_flag=0` and `var_flag=1`.
At `var_flag=0` the KL reduces to `0.5*||mu||^2` — a mild L2 penalty (CLAUDE.md,
landmine 1). At `var_flag=1` the variance term enters and dominates, contributing
~220 of a ~225 total loss. So E2 vs `e1_vsae_ref` at "matched beta" compares two
very different penalty strengths. **As configured, E2 cannot distinguish "a
genuinely variational SAE collapses" from "beta = 1.0 is far too large once
sampling is switched on."** Answering that needs a beta sweep at `var_flag=1`,
which is not in the pre-registered battery.

**Consequence for the pre-registered primary metric.** `frac_alive` is 1.0 for
every E2 seed, and `features_used` will likewise come out near the full 2048 — but
those features carry no information, since mu is zero and z is essentially prior
noise. **Live-feature fraction is not a validity-preserving metric on this arm**: it
will read "no feature death at all" for a model that reconstructs nothing. Any E2
falsification test keyed on live-feature count should be recorded with
`confounders_uncontrolled` (reconstruction collapse) and therefore excluded from
the evidence product, rather than reported as a null. This does not affect E0/E1,
where FVE is 0.85-0.90 and the metric means what it usually means.

## 7. E1 is confounded: the two arms do not apply the same penalty

**This is the arm that tests CLAUDE.md's landmine 1. As configured, it cannot.**

The claim under test is that a fixed-variance vSAE *is* a TopK SAE with an L2
activation penalty, because at `sigma = 1` the KL reduces to `0.5*||mu||^2`. E1
therefore trains `e1_penalty` (TopK + `activation_penalty=1.0`) against
`e1_vsae_ref` (vSAE, `var_flag=0`, `kl_coeff=1.0`) and expects them to be
indistinguishable. Measured over 6 seeds each:

| metric | `e1_penalty` | `e1_vsae_ref` | diff | d (across-seed SDs) | exact p (2-sided) |
|---|---|---|---|---|---|
| `frac_variance_explained` | 0.846130 | 0.889462 | -0.0433 | -58.9 | 0.00216 |
| `frac_recovered` | 0.929189 | 0.952204 | -0.0230 | -43.8 | 0.00216 |
| `frac_alive` | 1.000000 | 0.890951 | +0.1090 | +37.1 | 0.00216 |

They are wildly distinguishable. **But this is not evidence against the degeneracy
claim, because the two penalties are not the same intervention.**

**The KL is annealed; the activation penalty is not.**
`VSAETopKTrainingConfig.kl_warmup_steps` defaults to `int(0.1 * steps)` = 1000, and
`total_loss` multiplies the KL by `kl_scale = kl_warmup_fn(step)`, a linear ramp
from 0. Confirmed in the run logs:

```
Step 0     kl_scale=0.0000
Step 1000  kl_scale=1.0000
```

`top_k_with_feature_penalty.py` applies `activation_cost` at full strength from
step 0 with no scale factor of any kind. So over the first 10% of training the
vSAE arm carries a penalty ramping 0 -> 1 while the penalty arm carries a constant
1.0. The arms differ in the schedule of the very quantity the experiment is
supposed to hold fixed.

A second, smaller mismatch: `_compute_kl_loss` clamps to `[-10, 10]` before
squaring; the activation penalty does not clamp at all.

**Consequence.** The E1 comparison as run confounds "L2 penalty vs fixed-variance
KL" with "constant penalty vs annealed penalty". The difference above is
consistent with either. E1 should be recorded with `confounders_uncontrolled =
("kl_warmup_steps",)` and therefore **excluded from the evidence product** under
the framework's own rule, exactly as the preprint's SCR/TPP results are.

**What it would take to fix.** `kl_warmup_steps` is not exposed on either
`ExperimentConfig`, so it cannot currently be matched through `run_arm.py`. Either
add the field and set it to 0 for `e1_vsae_ref`, or add a matching warmup to the
penalty trainer. One line of config plumbing, then re-run 12 runs (~12 min at the
measured rate). This decision belongs to the author, so it is left undone.

**Also note the equivalence-margin problem.** E1 is an equivalence claim, and
PROJECT.md lists the margin as an open decision. The across-seed SDs measured here
are ~0.0004-0.0009, so a difference of 0.001 already sits at d = 2 and would be
"significant". Without a pre-specified margin in *scientific* units, the test will
reject equivalence for differences far too small to matter. The margin must be set
before this arm is interpreted, and it cannot be chosen now that the numbers above
have been seen.

## 8. The pre-registered primary metric saturates and carries no signal at d=2048

**Status: confirmed on the baseline; a working substitute is implemented.**

`features_used` — "dictionary entries selected at least once over the streamed
sample" — is the pre-registered live-feature metric, and RUNBOOK.md instructs
using `--n-samples 1000000` for every checkpoint so the counts stay comparable.
At this configuration it **saturates completely**:

```
baseline seed1:  features_used = 2048 / 2048   features_never_selected = 0
                 mean_selection_frequency = 0.125
```

`mean_selection_frequency` is exactly `k/d = 256/2048` — an arithmetic identity,
since TopK selects exactly k features per sample. With every feature firing ~12.5%
of the time on average, "selected at least once in 1e6 samples" is met by
essentially everything. **Corrected once all 24 checkpoints were in:** it saturates for three arms of
four, not all. Measured `features_used` over 6 seeds each:

| arm | mean | sd | verdict |
|---|---|---|---|
| baseline | 2048.00 | 0.000 | saturated |
| e1_penalty | 2048.00 | 0.000 | saturated |
| e2_learned_var | 2047.83 | 0.408 | saturated |
| e1_vsae_ref | 1943.67 | 8.571 | **discriminates** (91-117 dead) |

So the metric is not uniformly dead, and baseline vs `e1_vsae_ref` is a valid
pre-registered test (p = 0.00216, its exact two-sided minimum). But:

* baseline vs `e1_penalty` is **degenerate** — both groups are the constant 2048,
  so there is literally nothing to permute and no p-value exists.
* baseline vs `e2_learned_var` returns **p = 1.000**, a false null: E2's model is
  destroyed (FVE = 0.0001) yet reads as 2047.8/2048 features "alive".

**This is not a null result; it is a measurement failure.** The same run's
per-feature frequency distribution is strongly bimodal and shows a large
near-dead population that `features_used` cannot see:

| selection frequency | features |
|---|---|
| [0.00, 0.02) | **1547** (75.5%) |
| [0.30, 1.00] | 501 (24.5%) |
| between | 0 |

So three quarters of the baseline dictionary fires in under 2% of samples while
the pre-registered metric reports zero dead features.

**Why the preprint's numbers did not hit this.** Its dead-feature counts
(1474/7379 of 8192) come from Pythia checkpoints at `d=8192`, where
`k/d = 256/8192 = 0.031` — four times sparser per feature, so the "at least once"
criterion still discriminates. The gelu-1l sweep configuration used for every arm
here is `d=2048`, and the metric does not transfer to it. **The sample-size
warning in CLAUDE.md is right but incomplete: `features_used` is dictionary-size
dependent too, and the interaction is what breaks it.**

**Substitute, implemented in `falsification/report_summaries.py`.**
`liveness()` reads `feature_selection_counts` from the `all_histograms_*.npz` the
analyzer already saves — **one exact integer per feature**, so there is no binning
limit and no re-analysis is needed. (An earlier version of this note said only a
50-bin histogram was stored and used its coarse first bin; that was wrong, the
exact counts were there all along.) It reports the fraction of features selected in
under `rel * (k/d)` of samples. Measured minimum counts make the situation plain:

| arm | min selection count (of 1,000,192) | fraction < 0.1x k/d |
|---|---|---|
| baseline | 101-210 | 0.753 |
| e1_penalty | 4,765-10,424 | 0.0005-0.0010 |
| e1_vsae_ref | 0 | 0.417-0.429 |
| e2_learned_var | 0-4 | 0.996-0.999 |

Not one baseline or `e1_penalty` feature is close to dead, yet three quarters of
the baseline dictionary fires below a tenth of its expected rate. The one caveat
that remains: the threshold was chosen **after**
seeing that the pre-registered metric was degenerate, so under the project's own
pre-registration rule (PROJECT.md, simulation finding 2) any test built on it is
**exploratory and must be excluded from the evidence product** until the threshold
is pre-registered (REMEDIATION.md, F8b). The honest report
is that the pre-registered live-feature test cannot be run at this dictionary
size, not that it returned a null.

## 9. E3 checkpoints are trained but cannot be loaded: `VSAETopKMasked` has no loader

**Status: 6 checkpoints trained successfully, 0 analysable. Left unfixed, deliberately.**

All 6 `e3_masked_kl` runs trained without error, but every one failed analysis. Two
distinct defects, uncovered in sequence:

**(a) The saved config had no `dict_class`.** `VSAETopKTrainer.config` in
`vsae_topk_masked_kl.py` is documented as being "for wandb logging", but it is what
`trainSAE` serialises to `trainer_0/config.json`, and `load_dictionary()` dispatches
on `config["trainer"]["dict_class"]`. The property omitted it, along with
`layer`, `lm_name` and `submodule_name`. Result: `KeyError: 'dict_class'`.

The missing `submodule_name` is the dangerous one. The analyzer reads it as
`config["trainer"].get("submodule_name", "blocks.0.mlp.hook_post")` — so had
`dict_class` alone been supplied, analysis would have **succeeded while reading
activations from the wrong hook**, since every arm here uses
`blocks.0.hook_resid_post`. A silent wrong answer rather than an error.

*Fixed:* the `config` property now emits `dict_class`, `trainer_class`, `layer`,
`lm_name` and `submodule_name`. The 6 existing `config.json` files were repaired
in place with values copied from each run's own `experiment_config.json` (weights
untouched; each carries a `metadata_repaired_note`).

Note the value must be `VSAETopKMasked`, **not** `VSAETopK`: the latter dispatches
to `trainers/vsae_topk.py`, which applies the `F.relu(mu)` this trainer omits.
The obvious guess would have silently loaded the wrong architecture — the very
confound E3 exists to study.

**(b) The `VSAETopKMasked` branch calls a method that does not exist.**
`utils.load_dictionary()` does
`from .trainers.vsae_topk_masked_kl import VSAETopK; VSAETopK.from_pretrained(...)`,
but that class defines no `from_pretrained` — only `vsae_topk.py`'s sibling does:

```
AttributeError: type object 'VSAETopK' has no attribute 'from_pretrained'
```

**So this loading path has never worked, and no masked-KL checkpoint has ever been
loaded by this repo.** Any prior statement about masked-KL results should be
checked against how those numbers were actually produced.

**Why this is left undone.** Fixing it means writing a `from_pretrained` for the
masked class — new model-loading code (state-dict shape detection, `var_flag`
auto-detection, k extraction, optional decoder normalisation). Getting any of that
subtly wrong yields plausible but incorrect numbers, which is worse than none, and
E3 is confounded regardless: it needs the `F.relu(mu)` mismatch resolved before its
output means anything (`CLAUDE.md` landmine 2). Both changes should be made and
reviewed together, then the 6 checkpoints re-analysed — no retraining needed, they
are on disk and valid.

The other 24 checkpoints (baseline, E1, E1-ref, E2) analysed cleanly.

## 10. Two further defects in the masked-KL script, found by fixing item 9

Fixing the `dict_class` omission exposed two more, each hidden behind the last.

**(a) `evaluate_model()` died on the same missing key.** E3's own post-training
evaluation calls `load_dictionary` on the checkpoint it just wrote:

```
2026-09-02 05:59:40 - INFO  - Evaluating trained model...
2026-09-02 05:59:40 - ERROR - Evaluation failed: 'dict_class'
```

The run still wrote `RUN_COMPLETE.json` and the sweep recorded it as `ok`. **All 6
E3 runs reported success while producing no `evaluation_results.json` at all** —
the failure was caught, logged, and discarded. Same swallow-and-continue pattern
as the evaluation OOM in item 4: the only signal that anything went wrong is an
absent file.

**(b) `math` was never imported.** With `dict_class` fixed, evaluation got further
and then died at the NaN/inf guard in `evaluate_model()`:

```
NameError: name 'math' is not defined
```

The metrics had already been computed; only the logging loop that formats them
needed `math.isnan`. So the evaluation was doing all its work and throwing it away
one line before writing the file. `train_topk.py` and `train_vsae_topk.py` do not
use `math` at all, so this is unique to the masked script — which is consistent
with it never having been run to completion.

*Both fixed.* `import math` added; the `config` property now emits `dict_class`.
The 6 E3 checkpoints were retrained (~1 min each) rather than left on hand-repaired
metadata, so their `config.json` is written by the corrected code path and their
evaluation runs for the first time.

**What this says about E3's provenance.** Three independent defects — no
`dict_class`, no `from_pretrained`, no `import math` — each of which alone prevents
a masked-KL checkpoint from being evaluated or loaded. Together they are strong
evidence that **this trainer has never produced an analysed result in this repo**.
Any masked-KL number in the preprint or notes should be traced to how it was
actually generated before being cited.

## 11. Training is bit-deterministic given a seed

Verified because it was load-bearing: E3 seeds 1-4 were retrained *after* their
feature-usage summaries had been computed, so those summaries are only valid if
retraining reproduces the same weights. Hashing `ae.pt` for `e3_masked_kl` seed 5
before and after a `--force` retrain:

```
before: 1e48ced1d73ce69e
after:  1e48ced1d73ce69e
```

Bit-identical. Two consequences worth keeping:

* The affected summaries are valid; no re-analysis was needed.
* **E0's plumbing check gets a cleaner interpretation.** Exchangeability across
  seeds cannot be broken by run-to-run nondeterminism, because there is none. Any
  failure of exchangeability that E0 detects would have to come from the metric
  pipeline — a filename-ordering dependence, a shared data order, a cached
  artifact — which is exactly the class of bug E0 exists to catch.

Distinct seeds do produce distinct models (mean |diff| ~0.049 between baseline
encoder matrices), so the permutation test has real randomness to work with; the
determinism is *within* a seed, not across.

| e3_masked_kl | 0.8939 ± 0.0008 | +0.9570 ± 0.0007 | 1.0000 | 2048.0 | 0.1308 |

Across-seed SDs are ~1e-3 throughout, so every between-arm contrast is enormous in
d units and every non-degenerate permutation test lands on its exact floor.

Two observations that are *not* yet conclusions, because the arms they involve are
confounded (items 6 and 7):

* **The L2 activation penalty does not kill features — it homogenises usage.**
  `e1_penalty`'s least-used feature still fires 4,765 times in 1e6 samples, and its
  fraction below a tenth of the expected rate is 0.0008 against the baseline's
  0.754. The degeneracy story predicts feature *death*; what appears is the
  opposite, a dictionary pushed toward uniform utilisation.
* **Masked-KL reconstructs better than the unmasked fixed-variance vSAE**
  (FVE 0.8939 vs 0.8895, `frac_recovered` 0.9570 vs 0.9522) — but that comparison
  is exactly the one confounded by the missing `F.relu(mu)` (landmine 2), so it
  licenses nothing until F9b is decided.

## 13. E1 resolved: the degeneracy algebra is exactly right, the implementations are not

Three steps, each narrowing what the E1 difference can be attributed to.

**Step 1 — the schedule confound was real and it was large.** With
`kl_warmup_steps=0` applied to `e1_vsae_ref` (both arms now at constant full
penalty from step 0; `kl_scale = 1.0000` at step 0, verified in the log), the arms
were retrained and re-analysed. Against the archived pre-correction runs:

| metric | d, warmup=1000 (confounded) | d, warmup=0 (matched) |
|---|---|---|
| `frac_variance_explained` | -58.9 | -50.2 |
| `frac_recovered` | -43.8 | -39.0 |
| `frac_alive` | **+37.1** | **+6.2** |
| fraction < 0.1x k/d | -182.1 | -129.0 |

The warmup accounted for roughly **94% of the live-feature gap** (0.1090 -> 0.0064)
and only ~10% of the reconstruction gap. Since live-feature count is the
pre-registered construct, the confound was doing most of its damage exactly where
it mattered most. Flagging it was not pedantry.

**Step 2 — but the arms still differ, so what is left?** Even matched, d = 39-129
on every metric. So either the loss functions are not equivalent after all, or
something outside the loss differs.

**Step 3 — the loss functions are provably identical.** Both trainers were
instantiated with the same shapes and the vSAE given the TopK model's exact
weights, then run on one batch:

```
TopK    activation_cost     = 511.895264
vSAE    kl_coeff * kl_loss  = 511.895264      ratio 1.000000
TopK    l2_loss  = 835.336853
vSAE    mse_loss = 835.336853
```

Identical to six decimals. **`CLAUDE.md` landmine 1's algebra is exactly correct**:
at `var_flag=0` the KL reduces to `0.5*||relu(enc(x))||^2`, which is precisely what
`activation_penalty` computes — `mu` is post-ReLU (`mu = F.relu(self.encoder(...))`,
`vsae_topk.py`), so even the ReLU matches. A fixed-variance vSAE's loss **is** a
TopK loss with an L2 activation penalty.

**So the residual difference is architectural, and it is this:** the two trainers
use different bias parameterisations.

| | encoder input | reconstruction | params |
|---|---|---|---|
| `top_k_with_feature_penalty` | `relu(encoder(x - b_dec))` | `decoder(f) + b_dec` | tied pre-bias `b_dec` |
| `vsae_topk`, april mode (**what every vSAE arm used**) | `relu(encoder(x))` | `decoder(f)` + `decoder.bias` | untied `decoder.bias`, **no pre-bias** |

One centres its input on a learned pre-bias before encoding; the other does not.
That changes what the encoder sees and therefore which features fire — the obvious
candidate for a live-feature difference. `TopKConfig` has no april-mode option and
always uses the pre-bias form.

**Conclusion for the record, stated carefully.** The degeneracy claim is **true as
algebra and unproven as an empirical claim about checkpoints**. "The evaluated vSAE
is a TopK SAE with an L2 activation penalty" is correct about the objective and not
yet demonstrated about the trained models, because the two implementations were
never matched on parameterisation. This is a sharper and more useful result than
either "confirmed" or "refuted".

**The fix is available and is one line.** `use_april_update_mode` is already a
field on `train_vsae_topk.py`'s `ExperimentConfig` and reachable from
`run_arm.py`; setting it to `False` makes the vSAE subtract `self.bias` before
encoding, matching the TopK form. That is a design decision (see REMEDIATION.md
F7c), not something to change silently, and the non-april path is less exercised
so it needs its own canary.
